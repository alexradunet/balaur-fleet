# Setup, piece by piece

For a Duet that already runs NixOS (installed with the graphical installer, "erase disk").
Each stage says **what** you do, **why**, and **how to check** it worked. Do them in order
and stop at the first check that fails.

Nothing in stages 0-4 changes your running system. Stage 5 is the first one that does, and
it is reversible (the old system stays in the boot menu).

---

## Stage 0: Look at what you have

The config needs four facts about your install. Run this in a terminal on the Duet:

```bash
whoami
findmnt -no TARGET,SOURCE,FSTYPE /boot /boot/efi
lsblk -f
grep -E 'stateVersion|systemd-boot|grub|efiSysMountPoint' /etc/nixos/configuration.nix
```

| You learn | Why it matters |
|---|---|
| `whoami` (your username) | Becomes `balaur.user`. If it is missing from the config, NixOS removes that account on the next rebuild. |
| Where the EFI partition is mounted (`/boot` or `/boot/efi`) | The config uses systemd-boot. If yours is `/boot/efi`, you add one line (stage 3). |
| `stateVersion` | Keep the value your install chose; do not "upgrade" it by hand. |
| Whether `lsblk -f` shows `crypto_LUKS` | A disk-encrypted server waits for a passphrase on every reboot, including after a power cut. Fine for a laptop, awkward for a server. Tell me if you see it. |

## Stage 1: Get git, gh and flakes (temporarily)

A fresh NixOS has none of these set up. This only affects the current shell:

```bash
export NIX_CONFIG="experimental-features = nix-command flakes"
nix-shell -p git gh
```

You are now in a shell that has `git` and the GitHub CLI `gh`.

Log in to GitHub once (the Duet has no browser, so use the device-code flow):

```bash
gh auth login
```

Choose **GitHub.com**, then **HTTPS**, answer **Yes** to "authenticate Git with your GitHub credentials", then **Login with a web browser**. It prints a one-time code and a URL: open the URL on your phone or PC, type the code, approve. Check with `gh auth status`.

## Stage 2: Fetch the config and add *your* hardware file

```bash
gh repo clone alexradunet/balaur-fleet
cd balaur-fleet
cp /etc/nixos/hardware-configuration.nix hosts/tablet/
git add hosts/tablet/hardware-configuration.nix
```

- `hardware-configuration.nix` was generated by the installer from your real disks. The repo
  uses it automatically when present.
- `git add` is required: flakes only see files git knows about.

Check: `ls hosts/tablet/` shows `hardware-configuration.nix`.

## Stage 3: Edit the one file that is yours

```bash
nano modules/hosts/tablet.nix
```

Set, using what you learned in stage 0:

```nix
  time.timeZone = "Europe/Bucharest";     # yours
  system.stateVersion = "26.05";          # required: exactly what your install wrote

  balaur = {
    user = "alex";                        # from `whoami`
  };
```

- **SSH is key-only** (`balaur.ssh.passwordAuth` defaults to false). Add the machine's `userKeys` to its `fleet.<host>` entry (with a keyboard at the machine until then; Tailscale SSH is off). To bootstrap with a password instead, set `balaur.ssh.passwordAuth = true` for the first rebuild.
- If stage 0 showed the EFI partition at `/boot/efi`, also add at the top level of the file:
  `boot.loader.efi.efiSysMountPoint = "/boot/efi";`

Save in nano with Ctrl+O, Enter, Ctrl+X.

## Stage 4: Build it without switching to it

```bash
df -h /                                   # want 15+ GB free
nixos-rebuild build --flake .#tablet
```

This evaluates the config and downloads/builds everything (a few GB, mostly Chromium), then stops. It does **not** touch the running system.

Check: it ends without `error:` and leaves a `result` symlink. Errors here are safe; send
me the text.

## Stage 5: Install it for the next boot

```bash
nixos-rebuild boot --flake .#tablet --sudo
reboot
```

- `boot` (not `switch`): the new system takes effect only at reboot, so it does not tear
  down the desktop you are sitting in.
- `--sudo`: evaluates as your user (so git is happy) and uses sudo only to activate.
- **Undo**: the systemd-boot menu lists previous generations. Tap Space/arrow keys while it
  appears and pick the older one.

## Stage 6: What you should see

Boot splash, then GNOME logs in by itself as the household account (`balaur.tablet.user`, default `home`):
the **Balaur** app, Firefox, Jellyfin and Gelly are in the dock. Swipe up for the app switcher.

| Problem | Do this |
|---|---|
| Black screen / no desktop | Plug in a keyboard, press Ctrl+Alt+F3, log in, then `journalctl -u display-manager -b` |
| A service shows "Failed" on the Balaur app's Home page | `systemctl status <its unit>`; the page shows `systemctl is-active` live |
| Can't log in at console | Your old password still works for your old username (`balaur.user`) |

## Day to day

```bash
cd ~/balaur-fleet
nano modules/hosts/tablet.nix        # or any module
nixos-rebuild switch --flake .#tablet --sudo
git add -A && git commit -m "..."  # the repo is your system's source of truth
```

## Stage 9: Code on the Duet

The agent harnesses come from [numtide/llm-agents.nix](https://github.com/numtide/llm-agents.nix)
(updated daily, pre-built in a binary cache), not from nixpkgs, which lags by months:
`claude` (Claude Code) and `pi` ([pi.dev](https://pi.dev)).

**The first rebuild after adding them** should use the numtide cache so nothing compiles on
the Duet. The flake declares the cache, but Nix asks you to accept flake-provided settings
once:

```bash
cd ~/Projects/balaur-fleet && git pull
nixos-rebuild switch --flake .#tablet --sudo --accept-flake-config
```

(After that first switch the cache is part of the system config, so the flag is not needed.)

**The sessions live on the Duet.** Its `dev-host` aspect runs the server of `herdr`
([herdr.dev](https://herdr.dev)), the terminal workspace manager for agent sessions, from
boot (`systemctl --user status herdr-server`), and the server owns every terminal and
agent. The other machines are only screens:

```bash
dev                     # on any machine of the fleet: attach to the sessions on the Duet
cd ~/Projects/balaur-fleet
claude                  # first run: follow the login prompt (open the URL on another device)
pi                      # the OS agent, set up for the fleet's AI entryway (modules/agent.nix); nothing to log in to
```

`ctrl+b q` detaches (`ctrl+b ?` lists the keys); closing the terminal, the lid or the
whole PC does the same, and the agents keep working. `dev` again, from that machine or
another, shows them where they are. From a phone on the tailnet: `ssh alex@tablet` with
a key the Duet accepts (`balaur.sshKeys` in `modules/hosts/tablet.nix`), then `dev`.

The projects are cloned on the Duet, under `~/Projects`, and so are the logins (`claude`,
`pi`, `gh auth login`). Once, so that herdr can bring the agents back after a reboot:
`herdr integration install claude` and `herdr integration install pi`.

A deploy never restarts the server, since that would end every pane; a new herdr
starts with the next boot, or with `systemctl --user restart herdr-server`.

**Updating the agents** (they move fast):

```bash
cd ~/Projects/balaur-fleet
nix flake update llm-agents
nixos-rebuild switch --flake .#tablet --sudo
git add flake.lock && git commit -m "Bump agents"
```

`gh`, `ripgrep`, `fd`, `tree` and Node are installed system-wide. Per-project compilers and
toolchains should come from each project's own `nix develop` shell instead of system packages.

## Stage 10: Front camera

The `camera` aspect (already in the list in `modules/hosts/tablet.nix`) does four things:

1. Builds three patched kernel modules (`ipu-bridge`, `ov5675`, `intel_skl_int3472_discrete`) from the running kernel's
   source, so the front OVTI5678 sensor is recognised. The patch is `pkgs/camera-yoga-duet-ov5678.patch`; it
   is applied with zero fuzz, so a kernel bump that moves the code fails the build instead of misapplying.
2. Runs `duet-camera-relay`, which turns raw sensor frames into a v4l2loopback webcam named "Duet Front Camera"
   (`/dev/video64`), for any app that wants a webcam: GNOME's **Snapshot** shows it. The full image pipeline only
   runs while an app has the webcam open; otherwise the relay looks at 3 frames a second.
3. Watches those frames for movement and reports it (`/run/duet-camera-relay/motion`); the `duet-presence` service
   in the household session turns it into activity for GNOME, which keeps the screen on and wakes it
   (`balaur.camera.screenTimeout`).
4. Puts the camera on the Balaur app's Home page, opening Snapshot.

### Why the picture was yellow-green, and what fixes it

The front camera is an **RGB-IR** sensor (Lenovo: "IR + RGB hybrid", the same chip does the Windows Hello IR image).
Its colour filter repeats every 4x4 pixels and has **infrared pixels** where an ordinary camera has blue:

```
B G R G
G I G I      I = infrared
R G B G
G I G I
```

The kernel driver reports it as an ordinary 2x2 Bayer sensor, and libcamera has no RGB-IR support. So libcamera
reads the infrared pixels as "blue" and averages red and blue together as "red". No colour tuning can undo that,
which is why it looked yellow-green on both installs.

Windows gets it right because the IPU's hardware ISP, driven by Lenovo's tuning file, rebuilds R, G, B and IR,
subtracts the infrared that leaks into the colour pixels, then runs auto exposure, white balance, a colour matrix and gamma.
`duet-camera` (Go, in `camera/`) does those same steps on the CPU: raw frames from the IPU6 capture node in,
1280x720 YUYV out. It is the default (`balaur.camera.backend = "rgbir"`); `"libcamera"` brings back the old path.

### Apply, then calibrate once

This compiles the three modules (a minute or two). **Reboot** so the new modules load:

```bash
cd ~/balaur-fleet && git pull
```

```bash
nixos-rebuild boot --flake .#tablet --sudo
```

```bash
reboot
```

Check, in this order, and stop at the first failure (send me the output):

```bash
cat /sys/class/dmi/id/product_version            # 13ITL6 (or "Yoga Duet 7 13ITL6")
ls /sys/bus/acpi/devices | grep -i OVTI          # the sensor: OVTI5678:00
journalctl -k -b | grep -iE 'ipu|ov5675|int3472' # the driver bound, no "probe failed"
duet-camera probe                                # the media graph and the pipeline the relay uses
systemctl status duet-camera-relay               # active (running), logs fps / exposure / white balance
duet-camera-check                                # PASS: webcam is delivering a non-black image
```

**The 4x4 layout is already measured on this laptop** (default `GIGI/RGBG/GIGI/BGRG`: the relay log's tile statistics
put the infrared pixels at odd columns of even rows). The one thing left to confirm by eye is red vs blue: hold
up something clearly red. If it shows blue, switch to the other layout:

```bash
echo '{"cfa":"GIGI/BGRG/GIGI/RGBG"}' | sudo tee /var/lib/duet-camera/tuning.json && sudo systemctl reload duet-camera-relay
```

and pin it with `camera.tuning.cfa` in `modules/hosts/tablet.nix`.

To redo the measurement from scratch (another sensor, odd results), point the camera at something with clear
red **and** blue (a book cover, a towel), then:

```bash
sudo duet-camera-snapshot
```

```bash
duet-camera analyze -out ~/cfa "$(ls -t /var/lib/duet-camera/snapshots/*.raw16 | head -n 1)"
```

(If the relay won't start, take the raw frame with libcamera instead and analyze that file:
`sudo systemctl stop duet-camera-relay && cam -c1 --stream role=raw,width=2592,height=1944 -C4 --file=/tmp/raw#.bin`.)

It prints the brightness of each of the 16 tile positions (the IR ones are clearly darker indoors), marks the
layouts whose IR position matches with `*`, and writes one PNG per layout into `~/cfa`. Copy them to your
PC (`scp -r alex@tablet.local:cfa .`) and pick the one where red is red and blue is blue. Its layout goes in
`modules/hosts/tablet.nix`:

```nix
camera.tuning = {
  cfa = "GIGI/RGBG/GIGI/BGRG"; # the layout from the file name of the good PNG
};
```

To try a value without rebuilding, write it to the live overlay and reload (the Balaur app updates in a second):

```bash
echo '{"cfa":"GIGI/RGBG/GIGI/BGRG"}' | sudo tee /var/lib/duet-camera/tuning.json
```

```bash
sudo systemctl reload duet-camera-relay && journalctl -u duet-camera-relay -n 3
```

Other knobs, same way (defaults in `camera/config.go`):

| Key | What it does |
|---|---|
| `irCoeffs` | `[r, g, b]`: how much of the IR pixel to subtract from each colour. Raise if colours look washed out/pinkish under sunlight or halogen, lower if shadows turn green/black. |
| `ccm` | 3x3 colour matrix (row-major), after white balance. Undoes the crosstalk between the colour filters; without it (identity) the picture looks almost grey. Keep each row summing to 1 or whites get tinted. Default in `camera/config.go`. |
| `awbGains` | `[r, g, b]` to lock white balance; `null` = automatic. |
| `saturation` | 1.0 = as is. The quickest knob if colours are still too weak or too strong (try 1.2-1.4); in dim rooms it adds less colour noise than a stronger `ccm`. |
| `flipH`, `flipV` | Rotate/mirror in software (Snapshot already mirrors its preview like a selfie camera). |
| `aeTarget`, `maxGain`, `maxDigitalGain`, `antiFlicker` | Brightness target (0.18), analogue gain ceiling (8x), software gain once exposure and gain are used up (2x, dim rooms), mains frequency for flicker-free exposure (50 Hz; 60 in the Americas). |
| `view` | `"color"` (default); `"raw"`: grey picture straight from the sensor, no layout/IR/colour processing; `"noir"`: colour without IR subtraction. |

Then open Snapshot. "No camera found" means the relay or the device is missing; the **Camera**
row on the Balaur app's Home page shows the relay's state.

### If the preview is black

Look at what the relay says about its first frames:

```bash
journalctl -u duet-camera-relay -b --no-pager | tail -n 40
```

- **Restarting over and over / an error on every start**: the relay can't set up or start the capture. Send that output
  plus `duet-camera probe`.
- **"no signal (all pixels at or below black level)"**: frames arrive but are empty: a capture or exposure problem, not colour.
- **"WARNING cfa ... puts IR where the statistics see colour"**: the layout is wrong, so infrared subtraction is
  erasing the picture. Try the candidate it names (overlay below) or calibrate as above.

Two quick checks without rebuilding:

```bash
echo '{"view":"raw"}' | sudo tee /var/lib/duet-camera/tuning.json && sudo systemctl reload duet-camera-relay
```

A grey but properly exposed picture means capture works and only the colour settings are off.

```bash
echo '{"view":"noir"}' | sudo tee /var/lib/duet-camera/tuning.json && sudo systemctl reload duet-camera-relay
```

Colour without infrared subtraction: if this shows a picture and `"color"` doesn't, the layout or `irCoeffs` is the problem.
Remove the overlay afterwards with `sudo rm /var/lib/duet-camera/tuning.json && sudo systemctl reload duet-camera-relay`.

As a stop-gap, `balaur.camera.backend = "libcamera";` in `modules/hosts/tablet.nix` brings back the old (tinted) picture.

### Later: the Windows colour matrix

Lenovo's Windows camera driver for the 13ITL6 contains the sensor's tuning file (`.aiqb`) with colour matrices
measured in a lab. Once the layout above is right, those numbers can be extracted into `ccm`
for colour as close to Windows as this pipeline gets. That's a separate step.

## Stage 11: The voice assistant

The `assistant` aspect (in the list in `modules/hosts/tablet.nix`) adds a voice assistant to the household's
GNOME session. Only the wake word runs on the Duet; speech goes to Mistral (EU), and the fleet's pi, in its
home role, does the thinking:

| Piece | Where | Does |
|---|---|---|
| openWakeWord | on the Duet, 127.0.0.1:10400 | listens for "Hey Jarvis"; nothing leaves the house before it fires |
| balaur-assistant (`gnome/assistant/`) | on the Duet, a service of the GNOME session | microphone and speaker (PipeWire), timers, reminders, lists, memory, notifications; D-Bus `org.balaur.Assistant` |
| balaur-home-agent (`gnome/home-agent/`) | on the Duet, its child | pi in its home role: the model and the household's tools, and nothing else (no shell, no files) |
| Voxtral transcription (`voxtral-mini-transcribe-3-0`) | Mistral | what you said, Romanian or English |
| Chat model (`balaur`) | the fleet's AI entryway: zmeu's GPU first, Mistral second | what to do: answers and calls the tools |
| Voxtral TTS (`voxtral-mini-tts-3-0`) | Mistral | the voice |
| `web_search` tool (`mistral-medium-latest`) | Mistral | current facts |

Only the sentence after the wake word is sent (as audio for transcription), plus the text of the conversation.
Weather comes from Open-Meteo and news from RSS feeds, directly. No port is opened.

### Turn it on

Make a key at console.mistral.ai, then either:

- on the Duet: **Balaur** app → Assistant → ⚙ **Assistant settings** → Mistral API key → Apply. The key goes to
  the GNOME Keyring; the first time, GNOME asks for a keyring password: **leave it empty** (the household account
  has no password to unlock it with). The same dialog sets the model and the voices, and has a
  **Test** button.
- or from a terminal: `sudo balaur-assistant-login` (paste the key, hidden; it is checked, saved to
  /var/lib/secrets as the fallback, the voices are listed, the assistant restarts).

The defaults for model, voices and servers come from `balaur.assistant.*`; what you change in the app wins.

### Use it

Say **"Hey Jarvis"**, wait for the rising beep, speak. Examples:

- "Pune lapte și ouă pe lista de cumpărături." / "Ce am pe listă?"
- "Adaugă la treburi: dus gunoiul, Alex, până vineri."
- "Pune un timer de 10 minute pentru paste." / "Set a timer for 5 minutes."
- "Amintește-mi mâine la 8 să sun la medic." / "Remind me every Monday at 7 to take out the recycling."
- "Ține minte că Ana e alergică la nuci." (it also saves lasting facts on its own)
- "Cum e vremea mâine?" / "Ce știri sunt azi?" / "Who won the match last night?"
- "Mai încet." / "Stop." / "Gata."

Saying "Hey Jarvis" again interrupts it (speech, a slow answer, or a ringing timer). When it ends with a question,
it keeps listening for the answer without the wake word. While it listens or speaks, its orb and captions show
over every app; tap the orb to stop it. Timers and reminders also arrive as GNOME notifications with a **Stop**
button. The mic toggle is in Quick Settings ("Assistant"; off closes the microphone, and GNOME's mic indicator
goes away). The **Balaur** app shows the conversation (and you can type to it there), the lists, timers,
reminders and memory.

### Tuning

- Doesn't hear you from across the room: `balaur.assistant.audio.micGain` (default 65; 50 = 0 dB, max 70 = +20 dB).
- Wakes by itself: raise `balaur.assistant.wakeThreshold`. Misses you: lower it. `sudo balaur-wake-test` records a few
  tries and prints each one's score (`sudo balaur-wake-test all` compares the built-in wake words).
- What it heard, every tool call and the time to the reply:
  `journalctl _SYSTEMD_USER_UNIT=balaur-assistant.service -f` (or, as the household user, `journalctl --user -u balaur-assistant -f`).
- Location for the weather: `balaur.location` (also used by the ambient screen). News sources: `balaur.assistant.newsFeeds`.

### Custom wake word

Train one with the openWakeWord synthetic-data notebook (Google Colab, about an hour, no recordings needed;
search for "openWakeWord automatic model training"). Copy the resulting `hei_balaur.tflite` to
`/var/lib/balaur-wakewords/`, set `balaur.assistant.wakeWord = "hei_balaur";`, rebuild.

### Where things are kept

`~home/.local/state/balaur-assistant/` holds `house.json` (lists), `reminders.json` and `memory.json`, as plain
JSON. Timers live in memory only (a restart drops them). Keys are in the GNOME Keyring (and, if you used
`balaur-assistant-login`, `/var/lib/secrets/balaur-assistant-llm-key`). No audio is stored on the Duet.

## Stage 12: The ambient screen

When nobody has touched the Duet for a minute, the Shell extension covers the apps with a view that can be
read across the room. It shows:
- a big clock and the date;
- the weather for `balaur.location` (Open-Meteo);
- on the side, the fleet's machines (from Tailscale: online, or when last seen; this one's failed units) and
  the home's services (green running, grey stopped or not answering, red failed);
- the assistant's running timers, counting down, and the next reminder;
- a slow slideshow of the photos in the synced folder.

On the side in landscape; above the clock when the tablet is turned to portrait. A touch, click or key brings
back what was there. The tap that does it doesn't reach the app.

- **It stays up** while the camera sees movement, which keeps the screen awake. With nobody there, GNOME turns
  the screen off as before (`balaur.camera.screenTimeout`).
- **It stays away** while a window is full screen (a film), or while an app holds an idle inhibitor (a call,
  a player).
- **It is lean**: nothing is asked or decoded while it is hidden; the machines and services every 30 s while
  it is up.

### Photos

Put pictures in `photos` inside the Syncthing folder, on any machine of the fleet (`/srv/files/shared/photos`
on the tablet, the same folder under the synced one elsewhere), in any subfolders. Syncthing brings them to the
tablet; the slideshow lists the folder again every hour, so new ones show within the hour. JPEG, PNG and WebP
(not HEIC: export those as JPEG). Each is decoded at about the screen's size, off the Shell's main thread.

Without the synced folder (`balaur.tablet.ambient.photos.dir = null`), the slideshow uses Jellyfin's photo
libraries instead: an API key from the Jellyfin web UI (Dashboard → API Keys → **+**) given to
`sudo balaur-photos-login`, which also adds a **Photos** library for `/srv/media/photos`.

### Tuning

- `balaur.tablet.ambient.idleSeconds` (default 60; 0 = off), `balaur.tablet.ambient.photos.intervalSeconds`
  (default 30), `balaur.tablet.ambient.photos.dir`, `balaur.tablet.ambient.status` (default true). The
  extension reads `/etc/balaur/ambient.json` when the session starts, so after a change log the household
  account out and in again (or reboot).
- What it does: `journalctl --user -b | grep "balaur ambient"`, as the household user (weather, photo,
  status and inhibitor errors).
